# AI INSTRUCTIONS & PROJECT CONTEXT: SPORTA WEB-ADMIN

## 1. Project Overview
You are acting as a Senior React Developer and Enterprise Dashboard Expert.
This module (`web-admin`) is the Super Admin Portal for "Sporta", a sports facility booking and matchmaking platform. It is designed for system administrators to monitor global metrics, audit data, approve partners, and manage system configurations.

## 2. Web Architecture (Crucial Context)
- **The Concept:** This is a **Pure Web Application (SPA)**. Unlike the `web-owner` module, this app does NOT use Capacitor and is NOT wrapped as a mobile native app.
- **Responsive Strategy:** While the app must be fully responsive, the primary target environment is **Desktop/Large Screens** (for data density, data tables, and complex charts). The UI must degrade gracefully on tablets and mobile devices (e.g., converting wide data tables into stacked card lists on mobile).
- **Design Language:** The UI follows a strict **Minimalist-Tech** aesthetic (High contrast, generous whitespace, scannable data). We utilize a strict 60-30-10 color rule defined in `src/index.css`.

## 3. Tech Stack
- **Framework:** React 19 (Functional Components, Hooks) with `babel-plugin-react-compiler` for automatic performance optimization.
- **Build Tool:** Vite v8 (SWC).
- **Language:** TypeScript (Strict mode).
- **Styling:** Tailwind CSS **v4**. (Do NOT use `tailwind.config.js`. Rely entirely on `@theme` and custom variables defined in `src/index.css`).
- **State Management:** Zustand (for global UI state) and TanStack Query (for API caching, pagination, and data synchronization).
- **Icons & UI:** Headless UI approaches with modular reusable components.

## 4. Key Business Modules for this App
1. **Global Dashboard & Analytics:** High-level metrics viewing platform revenue, user growth, booking volume, and system health.
2. **Facility Auditing (Kiểm Duyệt Sân):** Workflows to review newly registered facilities. Includes verifying coordinates, checking operational slots, and triggering "Approve" or "Reject" status updates.
3. **User & Owner Management:** Data tables to list, filter, and search through all platform users and facility owners. Includes actions like banning, resetting passwords, or auditing activity logs.
4. **System Settings:** Forms to manage global configurations (e.g., platform commission rates, system-wide promotional banners).

## 5. Strict Coding Guidelines for AI
- **Tailwind v4 & Design Tokens:** ALWAYS use the CSS variables defined in the project (e.g., `bg-surface-container-lowest`, `text-on-surface`, `bg-brand-secondary`). Do NOT invent arbitrary HEX colors or use legacy Tailwind v3 syntax.
- **Component Architecture:** Maintain strict separation of concerns:
  - Put reusable generic UI components (Buttons, Modals, Tables, Badges) in `src/components/ui/`.
  - Put domain-specific logic and complex widgets in their respective feature folders (e.g., `src/components/facilities/`).
- **Type Safety (No `any`):** Always define precise TypeScript `interface` or `type` for API responses and component props. Handle nullable data correctly.
- **Data-Heavy Handling:** For components fetching data, ALWAYS implement and render 3 distinct states: Loading (Skeletons/Spinners), Error (Graceful fallback), and Empty Data states.
- **Scannable UI:** Data presented to admins must be highly scannable. Use appropriate font weights (`font-bold` for IDs/Key metrics) and color-coded tags (`Badge` components) for statuses (e.g., Active, Pending, Rejected).
